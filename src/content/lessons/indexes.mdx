Suppose a table holds a million users and you ask for the one with a certain email address. How does the database find it?

<Step>
Without any help, the database must do a **full scan**: read every row and compare its email to the one you want. With 1,000 rows this is instant. The bar shows the work: one check per row.
</Step>

<Step>
An **index** is an extra, sorted structure built on a column, much like the index at the back of a book. Because it is sorted, the database can jump straight to the right place instead of reading everything: finding one value takes roughly log₂(n) comparisons, about 10 for 1,000 rows. Real databases store the index as a **B-tree**, which packs many keys into each node, so in practice that is only a few disk reads.
</Step>

<Step>
Grow the table to 10,000 rows. A full scan now does ten times more work, while the indexed lookup needs only a few more steps. Each tenfold increase of the table adds just three or four more checks to an index lookup.
</Step>

<Step>
At 100,000 rows the scan checks a hundred thousand rows for a single result. The indexed lookup is still around 17 checks. The difference between "grows with the table" and "grows very slowly" is what makes some queries fast at any size.
</Step>

<Step>
At a million rows the contrast is dramatic: a million checks against about twenty. This is why a missing index is one of the most common reasons a page is slow once a table grows. (Real databases read in pages, so the exact numbers differ, but the shape is the same.)
</Step>

## Key takeaways

- An index turns a lookup from "check every row" into "follow a short sorted path".
- Index the columns you frequently filter, join, or sort on.
- Indexes are not free: they take storage and must be updated on every write, so add them where reads need them rather than everywhere.
